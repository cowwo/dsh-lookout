# ADR 0003：邮件通知收敛为最小功能面

- 状态：已采纳（未发版）
- 日期：2026-10-27

## 背景

邮件通知是三插件合并里体量最大的一块：8 个事件开关、发件人清单、SMTP 四件套（主机 / 端口 / 加密 / 账号）+ 6 家预设、授权码、收件人、直达链接与对外地址、发送队列，再外加一层「高级」折叠区和一份投递账本。跑了一段时间后，暴露的是三个不相干的毛病叠在一起：

1. **「高级」里的四个旋钮没人用，却每次都要被扫一眼**：合并窗口（`settleMs`）、完成时长下限（`minDurationMs`）、发送速率上限（`ratePerMinute`）、账本路径（`statePath`）。它们调的是内部时序，不是用户的意图；调错的后果是「悄悄收不到信」，而排错时还要先怀疑是不是自己拧过。合并窗口这类东西尤其违反直觉——用户想的是「我干完了你告诉我」，不是「你先等 1.5 秒」。
2. **投递账本是第二份过期真相**：它多出一条隐藏的写盘路径（每次投递都写），换来的是一块「最近一次投递」面板。但真正能定位问题的信息（SMTP 原始报错、尝试次数）在日志里更全；账本里那行摘要既不够看，又会和日志不一致。
3. **设置页越长，越找不到「为什么我收不到信」**：收件人、SMTP、授权码、事件开关、发件人、链接、高级——七块内容平铺在一个页面里，缺配置时只能自己去逐块找。页面顶部的判决条已经在回答「现在能不能发信」，但它被一堆旋钮稀释了。

结论：这四个旋钮和这份账本都不承担「用户想表达什么」，只承担「实现怎么调」。既然如此，就不该放在用户面前。

## 决定

把邮件通知收敛到「配好就能用、不用调参」的最小功能面。

### 1. 四个配置字段删除，改为代码内硬编码

| 被删字段 | 原作用 | 现在的实现 |
| --- | --- | --- |
| `settleMs` | 回合结束后的合并窗口 | 硬编码 1500ms |
| `minDurationMs` | 完成事件的最短任务时长 | 硬编码 2000ms |
| `ratePerMinute` | 全局发信速率上限 | 硬编码 10 封 / 分钟 |
| `statePath` | 投递账本落地路径 | 随账本一起删除，没有替代项 |

行为不变：合并窗口、时长门槛、限流照旧生效，只是不再暴露入口。

### 2.「高级」折叠区整层删除

设置页不再有这一层。原先放在里面的是上面四个字段，外加一个凭据引用名（`smtpPasswordRef`）的编辑框。删掉折叠区的代价：凭据**值**仍有正式入口，但改**引用名**只能手改 `settings.yaml` —— 这是一处轻微的能力缩水，接受它，因为改引用名属于极低频操作，换来的是设置页少一层折叠。

### 3. 投递账本整块删除

- 不再写任何投递文件（原先是 `$DSH_HOME` 下插件自己的目录）。
- 设置页的「最近一次投递」面板删除。
- Host 端点 `mailNotify/state` 删除，客户端不再有 `state` 这条 RPC。
- 发信失败改用日志排查：每次失败留一行 `logger.warn`，含邮件标签与错误原文；重试过程另有「第 N/3 次」的记录。
- 「发送测试邮件」保持不变：它本来就在当场返回成败与原始报错，是替代账本的那条正向排查路径。

### 4. 明确不动的部分

8 个事件开关（完成 / 出错 / 卡住 / 等审批 / 主动停止 / 系统中断 / 长度上限 / 子代理）、发件人清单与「用哪个发件人」、SMTP 四件套与 6 家预设、授权码、收件人、直达链接与对外地址、发送队列（串行 + 限流 + 退避重试）——全部原样保留。这次只删「调参面」和「历史面」，不删「表达面」。

### 5. 保留唯一判定入口

页面顶部的判决条继续负责「现在能不能发信、为什么不能」，删掉旋钮和账本之后，它是用户唯一的自检入口，因此它必须把缺失项直接说出来，而不是让人回下面逐块找。

## 后果

- **正面**：配置面从「一堆旋钮」收敛成「填完就能发」；设置页少一层折叠区、少一块面板；Host 少一个端点、插件不再写任何自有状态文件，也就不存在写坏的文件。行为保持原样。
- **负面**：想改那 4 个数字的人只能改代码；想回看「上次到底发没发出去」只能翻日志或点「发送测试邮件」，没有历史面板。
- **风险**：删字段属于破坏性配置变更——旧配置里残留的这 4 个键会原样留在配置对象里（schemastery 宽松模式），但不再被任何代码读取，不报错也不迁移；升级后设置页不会出现它们，行为按新的硬编码值走。若旧配置里曾把限流调小到 1 封 / 分钟来防炸邮箱，升级后回到 10 封 / 分钟，这类用户需要知道上限变宽了。
- **可观测性**：投递失败从「账本 + 日志」变成「日志一行」；日志里仍带尝试次数，重试过程也各有自己的 warn 行，按会话 id 就能串起来。
- **能力边界**：不再提供跨重启的投递历史，也不能重发历史里的某一封；判断「配置对不对」只剩两条路——判决条（静态判定）与「发送测试邮件」（真实投递一次）。

## 被否决的方案

1. **把发件人整块删掉（只用 SMTP 登录账号当发件人）**
   看上去能顺手再砍掉一个折叠区和一份清单，但发件人决定的是邮件抬头和回复地址，跟 SMTP 登录账号不是一回事：同一份 SMTP 凭据下可能要按用途换名字或别名（比如工作 / 个人、不同项目的通知抬头），删掉清单就只能硬编码一个身份。它属于「用户想表达什么」，不属于「实现怎么调」，跟本轮「只删调参面」的边界冲突，故否决。

2. **账本保留内存版（照样展示「最近一次投递」，只是不落盘）**
   能保住面板和一条写盘路径的删除，但内存账本重启即空：用户打开设置页看到「暂无记录」，最容易得出的结论是「发信坏了」，而不是「记录被清了」——这比没有面板更误导。而且面板里那行摘要本来就不如日志完整（没有原始报错、没有重试轨迹）。留一个半真的面板，等于把「排查」变成「猜」，故否决。

3. **把 8 个事件开关合并成一个「兜底开关」（要么全通知、要么全不通知）**
   实现上最省事，但 8 个事件的价值差别极大：主动停止多数时候是用户自己按的，没必要发信；子代理会话一次 workflow 能扇出几十个，必须能单独关；等审批恰恰是最需要立刻知道的一类。合并成一个开关，要么逼用户接受噪音，要么逼用户关掉全部通知——两种结果都会让人直接弃用这个功能。开关属于用户意图，不在收敛范围内，故否决。
