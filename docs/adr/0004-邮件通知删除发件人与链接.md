# ADR 0004：邮件通知删除发件人与链接

- 状态：已采纳（未发版）
- 日期：2026-10-27

## 背景

ADR 0003 把邮件通知收敛到「最小功能面」，但当时划了一条线：只删「调参面」（四个内务旋钮）和「历史面」（投递账本），保留「表达面」——发件人清单、直达链接与对外地址都在保留名单里。这一轮把这三样也删了，因为跑下来发现它们不属于「表达面」，而属于「这个插件本来就不该做的两件事」：

1. **发件人清单和唯一的发送通道重叠**：本插件只剩 SMTP 一种发送方式，而 SMTP 的登录账号本身就是合法的 From。清单带来的实际后果是分叉——同一条配置里有的条目能发、有的被收件服务器以 550 拒掉，而用户很难从「发信人」这个词看出问题出在哪一条。多身份（工作 / 个人抬头）听起来有用，但在一个「会话跑完提醒你」的通知器里，几乎没有第四次发生。
2. **链接是「看上去能用、其实经常不能用」的功能**：它要同时满足三个前提——装了 `dsh-deeplink` / `dsh-session-link` 这类能识别链接的接收端、用户自己把「对外地址」填对、邮件客户端愿意把它渲染成可点按钮。缺任何一个，用户看到的就是一个点了没反应的按钮，或者一串在手机上打不开的 `127.0.0.1`。一个提醒邮件里最不该出现的，正是这种「给了入口但进不去」的东西。
3. **对外地址本身是错误面与泄漏面**：它把内部主机名与端口写进正文与 HTML，邮件被转发时一并带走；填错时又不会报错，只是默默生成死链。为一个可选按钮配一个必须手填、填错无感的地址字段，代价明显高于收益。
4. **页面仍然是一串平铺的块**：判决条 / 收件人 / 怎么发 / 什么时候发给我 / 可选设置。前四块回答「能不能发、发给谁、怎么发、发什么」，最后一块回答的是「要不要多一个身份、要不要多一个链接」——不是发送的必要条件，却是整页唯一「填不对就悄悄失效」的一段。

结论：发件人与链接都不是「实现怎么调」，也不是「用户必须表达什么」，而是插件不该承担的两项附加能力。既然是附加能力，就该整块拿掉，而不是继续留在设置页里让人反复判断。

## 决定

### 1. 六个配置字段删除

| 被删字段 | 原作用 | 现在 |
| --- | --- | --- |
| `senders` | 发件身份清单（显示名 + 地址） | 随清单一起删除，没有替代项 |
| `activeSender` | 清单里当前生效的那一条（按地址记） | 同上，不再有「选哪一条」 |
| `senderName` | 发件人显示名（早于清单的旧字段） | 固定用默认显示名，不可配置 |
| `fromAddress` | 发件地址（早于清单的旧字段） | From 的地址恒取 SMTP 账号 |
| `linkEnabled` | 邮件里是否附直达会话链接 | 邮件恒不含链接 |
| `publicBaseUrl` | 链接的对外地址（如 `http://127.0.0.1:3081`） | 随链接一起删除，没有替代项 |

行为变化按上面的「现在」一列执行；没有任何隐藏的旁路开关。

### 2.「可选设置」段与「发件人与链接」折叠区整块删除

- 整段消失：段标题、「发件人与链接」折叠区、身份列表、添加 / 编辑弹层、两个控件（链接开关、对外地址输入框）一起删，不留空壳。
- 页脚「恢复全部默认」保留。它管的是整张设置卡片的覆盖清理，不依赖这一段的任何字段。
- 删完之后邮件通知页从上到下只有四块：判决条 / 收件人 / 怎么发 / 什么时候发给我；折叠区只剩「还有 3 种情况」这一处。

### 3. 发信人就是 SMTP 账号

- From 固定拼成「默认显示名 <SMTP 账号>」；显示名沿用原先内置的默认名（`DSH 通知 / DSH Notification`），设置页不再暴露。
- 不能选发件人，也不能代发别的地址。想换抬头或换地址，只能换整套 SMTP 配置。
- 收件服务器拒收发件人（550 一类）时，报错文案不再指引「换个发件地址」，只指向 SMTP 账号与授权码——因为已经没有第二个地址可以换。

### 4. 邮件里不含链接

- 纯文本版删掉「直达会话」那一行；HTML 版删掉蓝色按钮以及它下面那行 URL。
- 渲染层不再拼会话链接，也不再读对外地址；邮件正文只留可读的会话 ID 作对照。
- **这是本轮最大的一处能力下降**：收到通知后不能在邮件里一键回到那个会话，必须自己到 DSH 侧栏里找。

### 5. 明确不动的部分

8 个事件开关与「还有 3 种情况」折叠层、收件人、SMTP 四件套与 6 家预设、授权码（含「引用名只能手改 settings.yaml」的现状）、判决条、发送测试邮件、发送队列（串行 + 限流 + 退避重试）——全部原样保留。这一轮只删「附加能力」，不动「必要能力」。

## 后果

- **正面**：设置页少一整段、少一个折叠区，用户要判断的东西只剩「发给谁、用哪个邮箱发、什么时候发」；配置里不再有两条互相打脸的发送身份；邮件不再泄露内部地址与端口；渲染层少一条依赖（不再需要知道 Web 地址）。
- **负面（能力下降）**：不能代发、不能换抬头（只有一个固定默认名）；不能一键回会话——手机上看信尤其明显，得自己开 DSH 找；也不能把某个会话的地址转给别人。这是主动接受的交换：用两项附加能力，换一页更短、更少误判的设置。
- **风险**：删字段是破坏性配置变更，旧配置里残留的这 6 个键会留在配置对象里（schemastery 宽松模式），但不再被读取，不报错也不迁移；升级后设置页不会出现它们，行为按新规则走。原先靠 `fromAddress` 代发（例如 no-reply 别名、群发专用地址）的人，升级后 From 会变成 SMTP 账号，可能被收件服务器以 550 拒；原先靠邮件链接进会话的人会发现信里少了那一行 / 那个按钮，而界面上不会有任何「已移除」提示——这需要在发版说明里写清楚。
- **可观测性**：不变。发信失败仍是日志里一行 warn（含邮件标签与错误原文，重试过程另有「第 N/3 次」）；判断配置对不对仍是判决条 +「发送测试邮件」。
- **能力边界**：邮件从此只是提醒，不是入口。它告诉你「哪个会话怎么了」，但不负责把你送过去。

## 被否决的方案

1. **只删发件人、保留链接**
   看上去能保住「一键回会话」，但链接要工作就得留着它自己的两个字段（直达链接开关、对外地址），「可选设置」段和那个折叠区就删不干净——本轮界面缩减的收益直接归零。而且链接那三个前提（接收端插件、填对外地址、客户端识别）一个都没变，死链风险原样留在页面上。删一半等于什么都没删，故否决。

2. **只删链接、保留发件人**
   发件人是整页成本最高的一块：旧字段迁移（`senderName` / `fromAddress` 回填）、列表选中态、添加 / 编辑弹层、地址校验、以及「清单里换了条目但 SMTP 不认」的 550 报错，全都挂在它身上。而它换来的只是「同一套凭据下换个抬头」这一低频用法，地址本身还绕不开 SMTP 账号。删掉它不损失任何一条实际能发出去的能力，故否决。

3. **保留清单、只把界面藏起来**
   藏界面之后，字段、迁移、校验、Host 侧解析逻辑一项没少，配置面缩减的账面上是假的；`settings.yaml` 仍可能被手改成界面管不到的状态，测试面也不减。更要紧的是「看不见但仍在生效」比删掉更难解释——用户会问「我以前设的那个发件人去哪了」。既然它不承担必要能力，就整块删除，故否决。
