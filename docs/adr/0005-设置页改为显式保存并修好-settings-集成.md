# ADR 0005：设置页改为显式保存，并修好 Settings 集成

- 状态：已采纳（未发版）
- 日期：2026-10-27

## 背景

合并之后，邮件通知的设置页一直有两层毛病叠在一起：一层是「看起来能填」，另一层是「填了等于没填」。

**症状**

1. 设置页打开就是一个错误态：状态行写着「这一页读不到本插件的配置」，字段全是默认值或空；收件人、SMTP 怎么填都回不到页面上。
2. 往设置页写配置根本不落地。页面拿 `settings.describe()` 的结果按写死的 `dsh-notify-p` 去认命名空间，认不到；写回时 Host 侧直接报 `No configurable plugin entry "dsh-notify-p"`。
3. 合并后那份投递账本里的 23 条投递，**全部**失败，错误一字不差：「配置不完整，未发信 / incomplete config: 收件人为空 / no recipients configured」（2026-10-25 07:04 至 10-27 10:15）。当时从账本上看，这就是「用户没填收件人」。
4. 9 月升级后配置像是被谁删了：`settings.yaml` 里那段 `dsh-notify-p`（收件人 3901137470@qq.com、`smtp.qq.com:465`、`tls`）升级后不再生效。现在能确认，这**不是用户操作失误**。

**根因：三条叠在 DSH 0.2.x 的 settings 契约上**

1. **没有导出 `Config`**。settings 服务的 `schema(entry)` 只读 `entry.fiber.runtime.Config`；插件入口没导出它，`describe()` 就把这个 entry 整条跳过——页面怎么可能读得到自己的命名空间？写回时自然也没有「可配置的入口」。
2. **字段没有标 `.volatile()`**。settings 的写入通道只放行 schema 上标了 volatile 的字段（`isVolatilePath`），其余一律 `Config field "x" is not volatile`。本插件当时 15 个字段一个都没标，等于整页只读。
3. **命名空间写死成 `dsh-notify-p`**。settings 的命名空间键是 **profile 入口 id**（`entry.options.id`），不是包名、也不是插件名。合并后 profile 里的入口 id 是 `lookout`（更早还用过 `mail-notify`），客户端和配置层却都写死旧名字——前两条修好了，这一条仍会让页面和目标对不上。
4. **连带的「丢配置」**。DSH 0.2.x 把 `settings.yaml` 一次性导入 profile patch：导入时按 section 名去找同名入口，`dsh-notify-p` 找不到，于是只留下一行 warn，整段配置停在 `settings.yaml.imported` 里。9 月的「配置消失」就是这一步，不是谁手滑删的。

这三条不是本插件独有的 bug，而是 0.2.x 之后「插件要接设置页」的三个必填动作。少任何一个，页面表现都像「插件坏了」，但坏的位置各不相同。

## 决定

### 1. 导出 `Config`，15 个字段全部标 `.volatile()`

- 插件入口具名导出 `Config`（由 `MailSchema` 生成），settings 服务据此为入口 `lookout` 建出可读可写的表单视图。
- 授权码本体不进 `Config`：只保留引用名 `smtpPasswordRef`，值仍走凭据库，配置文档里永不出现密钥。
- 15 个字段逐个标 `.volatile()`，一个不漏：

| 组 | 字段 | 说明 |
| --- | --- | --- |
| 总开关 | `enabled` | 关掉后只订阅、不动作 |
| 收件人 | `recipients` | 一行一个，兼容逗号 / 分号 |
| 子代理 | `includeSubagents` | 默认关（一个 workflow 能扇出几十个子会话） |
| SMTP | `smtpHost` / `smtpPort` / `smtpSecure` / `smtpUser` / `smtpPasswordRef` | 发件地址固定取 `smtpUser` |
| 事件开关 | `notifyCompleted` / `notifyError` / `notifyBlocked` / `notifyApproval` / `notifyAbortedByUser` / `notifyInterrupted` / `notifyMaxTokens` | 共 7 个 |

- 没标 volatile 的字段只读，这是 DSH 的契约，不是本插件额外加的锁；以后加配置字段，必须同时决定它要不要可写。

### 2. 命名空间按配置指纹认领

- 客户端不再写死 `NS`。打开页面时读 `settings.describe()`，用 **配置指纹** 认出本插件那一个命名空间：`value` 里**同时**有 `smtpHost` 与 `smtpPasswordRef` 的项就是本插件，拿到它的 `ns` 与 `revision`。
- **为什么不能按 schema 认领**：`describe()` 返回的 `schema` 是 `schema.toJSON()` 的快照，只有 `{uid, refs}`，拿不到字段名与类型——那 15 个字段的名字与类型在客户端根本无从比对。也就是说「按 15 个字段的签名去认」没有可读的数据源，注定找不到，只会把页面再次变成「读不到配置」。
- 指纹取在 `value` 上：它是活配置快照，键名直接可见。两个只有本插件才会同时声明的键（`smtpHost` 与 `smtpPasswordRef`），足以把这一条从别的命名空间里摘出来。
- 认领到的 `ns` 就是 **profile 入口 id**（本机是 `lookout`）。之后所有 `mutate` / `replace` 都用这个 `ns`，不再出现「写死包名」。
- **已知限制**：指纹只看配置、不看入口，匹配时**取第一个命中**。同一 profile 里并排装两份同源插件时，两条都会被认成同一份，页面只对着第一条读写；要分别配置，得让 profile 里只留一份。
- 认领失败时页面必须说人话（就是现在那句「这一页读不到本插件的配置」），不能静默显示一张空表单——空表单会让人以为默认值就是真相。

### 3. 设置页改成显式保存

- 页面状态分 **草稿（draft）** 与 **基线（baseline）**：编辑只改草稿；草稿与基线的差异数就是「有 N 项改动未保存」。
- 右上角是**保存组**：「保存」把全部差异合成**一次**写入（配置走 `settings.mutate`，授权码走 `credentials`）；成功后基线追上草稿，状态变成「已保存 · N 秒前」并每秒走字。「放弃改动」用基线覆盖草稿。
- 保存失败保留草稿与错误原文，按钮可以再点。**revision 冲突已经真的处理**：识别到冲突→自动重读最新一份→把用户草稿原样留在页面上→提示再点一次保存。**重试不再必然失败**，也**不吞草稿**、不假装成功。
- 「发送测试邮件」和「恢复全部默认」**不进保存事务**：
  - 判决条按**已保存**的配置判定；页面上有未保存改动时，读数直接说「未保存的改动不参与判定」，判决条不再拿草稿当答案。
  - 测试邮件随时可点，用当前**已经保存**的配置真发一封；按钮旁有明确提示写明这一点——草稿里没保存的改动不参与。
  - 恢复默认点下去就 `replace(ns, {})` 清空本插件的全部覆盖并立即生效，不经过保存按钮。
  - 理由：一个是在测「已保存的这套配置能不能发」，一个是「回到初始状态」，都不该被未保存的草稿影响。

### 4. 历史配置恢复

- 从 `settings.yaml.imported` 的 `dsh-notify-p` 段，把仍然存在的字段恢复进 profile `web` 的 `cordis.patch.yml`、入口 `lookout` 的 config：`recipients`（3901137470@qq.com）、`smtpHost`（smtp.qq.com）、`smtpPort`（465）、`smtpSecure`（tls）、`smtpUser`（3901137470@qq.com）、`notifyInterrupted`、`notifyMaxTokens`。
- 已删能力的字段不恢复：`publicBaseUrl` 随「邮件里的链接」一起删除（ADR 0004），恢复它只会造出一个没人读的键。
- `settings.yaml.imported` 原地保留，从此只作历史证据；插件不再读它，也不会再往 `settings.yaml` 写任何东西。

## 后果

- **正面**：设置页第一次真的能读、能写；不再靠「改完以为存上了」；投递失败不会再伪装成「收件人为空」；命名空间按配置指纹认领、键仍是入口 id，换 profile、改 id 都不会失联（并排装两份同源插件仍会并成一份，见决定 2 的已知限制）；9 月丢的配置有了来源，也能按证据恢复。
- **负面（多一次点击）**：改了不点保存就不生效。这是主动接受的交换——用一次点击，换「半填的配置不会立刻被运行时拿去发信」，以及一个能取消的编辑过程。
- **负面（volatile 写入不重跑 apply）**：保存只是改配置，**不会**让插件重新 `apply` 一遍。任何在 `apply` 时抓取并缓存下来的 config 都会变成过期真相——保存显示成功、行为却要等重启才变。因此判决条与测试邮件都必须**每次重新读已保存的活配置**，不能把启动时那份对象、更不能把草稿当真相。这是本次改动最容易被忽略的一条。
- **负面（一次写多字段）**：保存是批量写入，任何一个字段非法都会让整批失败；页面要指出是哪个字段，而不是只说「保存失败」。
- **负面（两条写入通道）**：配置与授权码分属 settings 与 credentials，只有两边都成功才配叫「已保存」；只成功一半必须标红说清，不能显示绿字。
- **风险**：`settings.yaml.imported` 从此只是证据，谁再改它都不会生效；DSH 若再调整 settings 契约（volatile 语义或命名空间规则），这一页仍可能整体失联——所以「读不到配置」那句话必须一直说人话，并保留重读入口。
- **可观测性**：保存失败有错误原文且可重试；发信侧仍是判决条 +「发送测试邮件」，两者都只认已保存的配置，草稿不参与，页面上也说清这一点。
- **能力边界**：这一页只负责「把配置写进去」，不负责「证明配置能发信」；后者永远是测试邮件的事。

## 被否决的方案

1. **继续即时保存（每个按键一次写入）**
   半填状态会立刻成为「已保存」：收件人输到一半、SMTP 还没填，运行时就已经拿到这份配置；此时只要有会话结束，投递就按半截配置失败，用户看到的是一串噪声。而且每字段一次 `mutate` 会带同一份 revision 互相打架，旧实现只能靠防抖和批量补丁绕开；授权码与配置也没法作为一个动作提交，误清一个输入框没有回头路。更直接的是「已保存 · N 秒前」失去意义——任何输入都会刷新它，用户无法判断到底存没存。故否决。

2. **写死入口 id `lookout`**
   这个 id 是 profile 的部署名，不是插件身份：本仓库历史上它从 `dsh-notify-p` → `mail-notify` → `lookout` 变过，换 profile、并排装两份、用户重命名入口都会立刻失联。写死它等于把「页面读不到配置」换个位置保留下来，这次错在 id 而不是包名，并且把部署细节泄漏进插件代码。故否决。

3. **让插件自己读写 `settings.yaml`**
   绕过 settings 服务就等于绕过 profile 分层（bundle 基础层 + patch 覆盖层）和 revision 协调：自己写文件会覆盖并发改动，也读不到基础层默认值。而 `settings.yaml` 在 0.2.x 已改成「一次性导入源」，导入后即改名 `settings.yaml.imported`——继续写它，写的是一个没人读的文件。密钥存储、导入迁移、schema 校验都得自己重做一遍，收益只是「不用导出 Config」，成本却是重写半个 settings 服务。故否决。

4. **只改命名空间，不补 `Config` 与 volatile**
   症状会从「读不到」变成「读得到、一写就报 not volatile」，等于只修了三分之一，还多出一层「看起来能改、其实改不动」的假象。三件事是同一个契约的三个位置，必须一起补齐。故否决。
